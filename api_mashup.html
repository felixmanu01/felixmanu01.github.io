Gig Radar API mashup.

A paper prototype for a service that combines two API sources. The goal is to help someone find a concert and understand the artist right away, before they decide to go.

Type
Paper prototype
APIs
Ticketmaster, MusicBrainz
Output
Three screens

The problem

Concert listings say what's on and when, but they don't help much if you don't already know the artist.

The idea

Put upcoming concert information and artist information in the same experience.

The value

The user goes from discovery to understanding without searching across several services.

The two API sources

Ticketmaster Discovery API

The first API finds events. It searches for events and returns details such as date, venue, artist and a link to the event.

Role
Find what's on
Data
Event name, date, venue, artist, genre and event link
In the prototype
Builds the list of upcoming concerts
Official documentation

MusicBrainz API

The second API looks up the artist found in the concert data. MusicBrainz returns metadata such as artist type, country of origin, tags and other identifiers.

Role
Explain who the artist is
Data
Artist name, type, area, country, tags and MusicBrainz ID
In the prototype
Adds artist information to each concert
Official documentation

How the mashup works

Ticketmaster

Fetches upcoming concerts in Stockholm and returns the artist name, date and venue for each event.

The artist name

The artist name from the event becomes the search query in MusicBrainz.

Gig Radar

Shows the concert details and the artist's metadata on the same card. That card is the mashup.

Paper prototype

Three steps in the user's journey. It isn't a working app; it shows how information from the two API sources would be used in a product.

Two data sources shown as one experience

Why it's a mashup

Two separate data sources combined into something neither offers on its own.

Ticketmaster answers what's on and where. MusicBrainz answers who the artist is. Gig Radar puts both answers in one user experience.

What I learned

API data needs a link

Two API sources don't automatically make a mashup. They need a shared value. Here the artist name links the event in Ticketmaster to the artist in MusicBrainz.

Prototype before code

The paper prototype makes it possible to test the idea and the flow of information before spending time on a working web app.

Data quality matters

The same artist name can be written in different ways. A real version needs to check that the right artist is matched between the sources.

Each source has one job

Ticketmaster handles events. MusicBrainz handles artist metadata. Each source does one clear part of the work.
